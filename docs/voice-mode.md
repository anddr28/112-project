# Голосовой режим: разговор оператора с ИИ-заявителем

Зафиксировано 2026-09-20. Это описание того, **что** мы строим и **почему именно так**;
контракты — в `contracts/openapi/` (v1.1), задачи по людям — в `docs/tasks/`.

## 1. Цель

ТЗ, п.1: «эмуляция вызова на гарнитуру IP-телефона оператора 112 с использованием ИИ».
Текстовая расшифровка реплик (что есть сейчас на фронте) закрывает пункт формально.
Голосовой режим закрывает его по существу и даёт то, чего нет ни у кого из конкурентов
и «аналогов нет» по словам заказчика:

1. **Студент слышит заявителя** (TTS) и **говорит в гарнитуру**.
2. **Заявитель — LLM в роли**: отвечает на вопросы оператора, паникует, не знает
   того, чего не знает, не выдаёт факты, о которых не спросили.
3. **Речь оператора распознаётся** (STT) и становится транскриптом.
4. **После сдачи карточки оценивается и разговор**: выполнил ли протокол опроса
   (адрес, пострадавшие, телефон, «помощь направлена»), темп, слова-паразиты, тон.

Итог для преподавателя: не только «что записал в карточку», но и «как разговаривал».

## 2. Сквозной сценарий (P0)

```
Студент                     go-core                        ai-service
  │ «Принять» ─────────────▶ call_accepted_at=now            │
  │ ◀── attempt + opening (turns[0], аудио из tts_cache)      │
  │ ▶ играет вступительную реплику                           │
  │                                                          │
  │ зажал PTT, говорит, отпустил                              │
  │ POST /attempts/{id}/dialogue/turns (webm/opus) ──▶        │
  │                            собирает контекст:            │
  │                            call_script+dialogue-бриф,    │
  │                            history, revealed_fact_ids    │
  │                            POST /v1/dialog/turn ────────▶ STT (faster-whisper)
  │                                                          │ LLM-заявитель (qwen, JSON)
  │                                                          │ TTS (Silero) → shared volume
  │                            ◀────── operator.text, caller.{text, tts, revealed…}
  │                            INSERT 2 реплики; WS → преподаватель
  │ ◀── DialogueTurnResponse {operator, caller{audio}}       │
  │ ▶ транскрипт в панели, играет ответ заявителя            │
  │ … повтор … параллельно заполняет карточку …              │
  │ «Сохранить» ───────────▶ submit: поля+тайминг мгновенно  │
  │                            ai_jobs: grammar, semantic, dialogue
  │                            ──▶ /v1/jobs/dialogue (транскрипт + чек-лист эталона)
  │                            ◀── callback dialogue{score, checklist, speech, tone}
  │ ◀── WS evaluationUpdated → страница результата            │
```

Ключевые свойства:
- **Push-to-talk (PTT), полудуплекс.** Студент удерживает кнопку/клавишу — запись;
  отпустил — отправка. Пока звучит заявитель, микрофон закрыт. Это убирает VAD,
  эхо и перебивания из P0. Режим «клик-старт/клик-стоп» — тот же код.
- **Синхронный ход диалога** — единственный синхронный путь в ai-service. Всё
  остальное остаётся fire-and-forget. Таймаут go-core → ai-service: 20 с.
- **ai-service stateless и здесь**: историю и раскрытые факты присылает go-core
  каждый ход. Перезапуск Python ничего не теряет.
- **Аудио оператора не хранится** (ни в Python, ни в Go): только транскрипт.
  Меньше ПДн, меньше диска, проще ТЗ по аудиту.
- **Текстовый fallback обязателен**: тот же эндпоинт принимает `text` вместо аудио.
  Это режим для машин без гарнитуры, для QA (детерминированные тесты диалога) и
  для демо при отказе микрофона.
- **Голос — настройка занятия**, не третий режим: `lessons.settings.voice
  {enabled, input: voice|text|both, pushToTalk, maxTurns, ttsEnabled}`.
  Режимы `cards` / `card_actions` не меняются. Вес слоя `dialogue` = 0, если голос выключен.

## 3. Что считает кто (дополнение к docs/contracts.md)

| Вычисление | Где | Примечание |
|---|---|---|
| STT реплики оператора | ai-service (faster-whisper по умолчанию; см. model-selection) | + ITN: «дом четырнадцать» → «дом 14» |
| Реплика заявителя | ai-service, LLM `dialog_fast` (3b), JSON-выход | дисциплина фактов: только `dialogue.facts` с учётом `reveal` |
| Озвучка ответа | ai-service, Silero, синхронно | препроцессинг чисел/сокращений обязателен |
| Хранение транскрипта, нумерация ходов, `revealed_fact_ids` | go-core | агрегат по репликам; студенту не отдаётся |
| Завершение разговора | go-core по `should_end` / `maxTurns` / «положить трубку» / submit | |
| Слой `dialogue`: чек-лист протокола, тон | ai-service, LLM `eval_dialogue` (7b по возможности) | по транскрипту + `expected_dialogue` эталона |
| Слой `dialogue`: речевые метрики (темп, паразиты, паузы) | ai-service, детерминированно, без LLM | считаются всегда, даже если LLM упала |
| Вес слоя, итог, XP | go-core | как и раньше |

## 4. Бюджет задержки (CPU, 8 ядер / 16 ГБ, один студент)

| Этап | Оценка | Чем ускоряем (P1) |
|---|---|---|
| Запись + сеть | ~0.1 с | — |
| STT, 5 с речи, whisper small int8 | 0.8–1.5 с | GigaAM-CTC (ONNX) быстрее и точнее на русском — проверить в bench |
| LLM 3b q4, ~600 tok промпт, ~50 tok ответ | 2.5–4 с | keep_alive, стабильный префикс промпта (кэш KV в Ollama), num_predict ≤ 80 |
| TTS Silero, 3 с речи | 0.3–0.6 с | по предложениям, первое отдаём сразу |
| **Итого** | **4–6 с** | цель P1: ≤ 3 с |

Скрываем ожидание реализмом: сразу после отпускания PTT фронт играет короткую
«заполняющую» реплику из кэша («Алло?.. да-да…», «ой, секунду») — пока LLM думает.
Это не костыль, а стандартный приём голосовых ботов.

**Многопользовательская нагрузка.** Полоса LLM одна. 20 студентов, говорящих
одновременно, — очередь: ход ждёт `dialog_waiting × ~3 с`. Что делаем:
- ходы диалога имеют абсолютный приоритет над фоновыми LLM-задачами (оценка,
  генерация ждут);
- `OLLAMA_NUM_PARALLEL=2..4` — батчинг декодирования на одной модели (веса общие,
  RAM хватает) — измерить в bench, это главный рычаг;
- при `dialog_waiting > DIALOG_MAX_WAITING` (дефолт 8) — 503 + Retry-After; фронт
  говорит «заявитель не отвечает, повторите» — **это не ошибка попытки**;
- честно документируем предел: «одновременных голосовых диалогов на CPU-стенде — N»
  (число из bench), для 20 одновременных — GPU или второй AI-узел.

## 5. Данные сценария под голос

Сценарий получает два новых блока (генерируются LLM, правятся преподавателем):

- `callScript.dialogue` — **бриф заявителя**: `persona`, `speakingStyle`,
  `facts[{id, text, reveal: volunteer|on_request|never, hints}]`, `unknowns`,
  `endConditions`, `maxTurns`. `keyFacts` остаётся плоской проекцией `facts[].text`.
- `expectedDialogue` — **чек-лист протокола**: `checklist[{id, text, kind:
  question|instruction|phrase|behavior, required, weight, hints}]`, `forbidden`.

Базовый чек-лист по категориям (пожар / ДТП / медицина / ...) — это знание
предметной области из памятки АРМ-112 и билетов; его собирает QA вместе с
питонистом и он живёт в промпте генерации как few-shot.

## 6. Что нужно от go-core (зависимости для остальных — для сведения)

Задачи ядра здесь не расписываются, но остальным нужно знать, чего ждать:

- миграция `00002_voice.sql`: `ai_jobs.type` + `evaluate_dialogue`;
  `evaluations.dialogue_score`, `evaluations.dialogue jsonb`; таблица
  `attempt_dialogue_turns(attempt_id, turn_no, speaker, text, source, confidence,
  audio_path, duration_ms, at, revealed_fact_ids)` (PK attempt_id+turn_no);
  `settings`: `score_weights.dialogue`, `voice`, `stt`;
- эндпоинты `frontend.v1.yaml` §dialogue, `/media/tts/{path}`, WS-каналы;
- оркестрация хода: сбор контекста → `/v1/dialog/turn` → запись → WS;
  идемпотентность по `turnNo`; таймаут 20 с; 503 → `caller_busy`;
- предгенерация TTS вступительной реплики и служебных фраз при `approve`;
- HTTPS для SPA (self-signed CA контура) — без него нет микрофона в браузере.

## 7. Границы P0 / P1 / P2

| | Состав |
|---|---|
| **P0 (демо 29.09)** | PTT-запись → STT → LLM-заявитель → TTS → транскрипт; текстовый fallback; слой `dialogue` в оценке (чек-лист + метрики речи); результат и отчёт с транскриптом; бриф и чек-лист в редакторе сценария; выбор моделей по bench; docker-образ ai-service с моделями офлайн |
| **P1** | заполняющие реплики; `OLLAMA_NUM_PARALLEL`; стриминг STT (partial-текст пока говорит); TTS по предложениям; предпрослушивание голоса в редакторе; ночная переоценка `eval_thorough`; live-транскрипт у преподавателя с аудио |
| **P2** | VAD вместо PTT (silero-vad в браузере через onnxruntime-web); прерывание заявителя; эмоциональная просодия TTS; несколько заявителей/фоновый шум; GPU-профиль |

## 8. Риски и что с ними делаем

| Риск | Митигация |
|---|---|
| STT путает адреса/числа | hints из легенды в `initial_prompt`; ITN; bench-метрика «точность адресных сущностей»; низкий confidence → не штрафуем в dialogue |
| LLM выдумывает факты / выдаёт всё сразу | JSON-выход с `revealed_fact_ids`, пост-фильтр: реплика не может содержать факт с `reveal=never`; тест-набор «утечки» в bench; temperature 0.3 |
| Задержка > 6 с убивает ощущение звонка | заполняющие реплики; num_predict cap; 1.5b как аварийный профиль |
| Микрофон не работает у половины стенда | текстовый fallback + pre-flight «проверка микрофона» перед занятием; HTTPS обязателен |
| Ollama не тянет диалог и оценку одновременно | приоритетная очередь LLM; фоновые задачи стартуют только при пустой очереди диалогов |
| Silero читает «д. 14» как «дэ четырнадцать» | препроцессор текста (num2words, раскрытие сокращений) — обязательная часть TTS-задачи |
