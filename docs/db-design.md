# БД тренажёра ДДС: решения и обоснования

Схема: [`db/migrations/00001_init.sql`](../db/migrations/00001_init.sql). PostgreSQL 12+ (ТЗ), миграции — goose.
Документ отвечает на вопрос «почему именно так, а не иначе» — по каждому существенному решению.

---

## 1. Что диктует ТЗ (требование → следствие для БД)

| Требование ТЗ | Следствие в схеме |
|---|---|
| Запись ≥100 оп/с; отклик ≤2 с при 100 пользователях; ≥20 сессий | Проектируем на **1000 оп/с** (запас ×10): батчинг событий, отдельная таблица черновиков, минимум индексов на горячем пути — §3 |
| Восстановление после сбоя сети ≤30 с **без потери данных** | Черновики (`attempt_drafts`), поток событий (`attempt_events`) как источник истины, идемпотентность по `client_seq` — Р5, Р6, Р7 |
| Аудит всех действий, журналы ≥6 мес | `audit_log`, партиционирован помесячно: ретеншн = `DROP PARTITION` — Р11 |
| RBAC (админ/преподаватель/обучающийся), «многоуровневая аутентификация» | `users.role`, `auth_sessions` (refresh + отзыв), lockout-поля |
| Изменение оценок только с фиксацией в аудите | `override_*` в `evaluations` + CHECK «нет override без причины и автора» — Р9 |
| Преподаватель валидирует сгенерированное; правит эталоны | Статусная модель `scenarios`; **иммутабельные версии** `etalons` — Р4 |
| Сохранять промежуточные результаты | `attempt_drafts` — Р7 |
| Профильные события по типу ДДС ученика | Справочник `services`, `users.service_id` |
| Рекомендации системы студенту; инсайты ИИ по группе | `recommendations` (scope student/group, source system/teacher, `evidence` для объяснимости) |
| Прогресс, история ошибок, статистика | `xp_ledger`+`levels`, VIEW `student_progress`, `student_category_stats`, `student_field_errors` — Р8, Р15 |
| Отчёты в Excel/PDF | `reports.format IN ('csv','xlsx','pdf')` |
| Пакетный импорт материалов/сценариев (опц.) | `import_batches` |
| Интеграция с локальной системой управления доступом | `users.auth_source ('local','ldap')` — задел, локальная аутентификация остаётся основной |
| Защита ПДн | `consent_given_at`; контракт редакции секретов в аудите (Р11); soft delete вместо физического удаления |
| Изолированный контур, минимум компонентов | Очередь AI-задач в самой PG, а не в брокере — Р12 |

## 2. Карта доменов

```
справочники:  services, classifier_categories, levels, settings
люди:         users, auth_sessions, groups, group_members
контент:      scenarios ──< etalons (версии), tts_cache, materials, import_batches
обучение:     lessons (class|practice) ──< lesson_categories / lesson_scenarios / lesson_participants
попытка:      attempts ──1 attempt_drafts, ──< attempt_events
оценка:       evaluations (1:1 к attempts), teacher_feedback, recommendations, xp_ledger
витрины:      student_progress, student_category_stats, student_field_errors (VIEW)
инфра:        ai_jobs, reports, backups, audit_log (партиции)
```

Главная цепочка: `scenario → etalon(version) → attempt → evaluation → feedback/xp` — на каждом шаге зафиксировано, **по какой версии чего** считали. Любую оценку можно объяснить задним числом; это же нужно QA модели для тюнинга промптов.

## 3. Нагрузка: расчёт и запас прочности

**Профиль.** Худший случай на порядок выше ТЗ: 200 одновременных студентов (ТЗ — 20 сессий), каждый в пике заполнения карточки генерирует ~5 событий/с (ввод в поля). Итого **~1000 записей/с**, почти все — `attempt_events` + upsert `attempt_drafts`.

**Математика.** Строка события ~300–500 байт → ~0.5 МБ/с WAL. Для NVMe из ТЗ (сервер: NVMe SSD) это фоновый шум: одиночный PostgreSQL на таком железе держит 10–20k простых записей/с. Вывод: **никакой экзотики не требуется** — требуется не мешать Postgres работать. Приёмы:

1. **Батчинг событий.** Go-ядро не пишет каждое событие отдельной транзакцией: копит 50–100 мс и пишет одним multi-values `INSERT` (или `COPY`). 1000 соб/с превращаются в ~10–20 транзакций/с. Это главный множитель производительности, он в контракте приложения, не в схеме.
2. **Черновики отдельно от попыток (Р7).** Самый частый UPDATE в системе идёт в таблицу без единого вторичного индекса, с `fillfactor 50` → обновления HOT (не трогают индексы, не пухнет heap).
3. **Минимум индексов на горячем пути.** У `attempt_events` — три индекса, каждый оправдан: `(attempt_id, at)` — выборка ленты попытки; partial unique `(attempt_id, client_seq)` — идемпотентность; BRIN по `at` — ретеншн и выборки по времени за ~48 КБ вместо гигабайтного btree.
4. **`synchronous_commit = off` per-transaction** для транзакций с событиями (риск — потеря ≤ пары сотен мс телеметрии при крахе сервера, допустимо); карточки, оценки, аудит — с `on`.
5. **`fillfactor 85` у `attempts`** — переходы статусов идут HOT-обновлениями.
6. **UUIDv7 (Р1)** — вставки в PK-индексы монотонны, без random-write bloat.

**Чтения.** Витрины прогресса — агрегаты по десяткам-сотням тысяч строк: миллисекунды. Требование ТЗ «отчёт ≤30 с» закрыто с запасом на порядки.

**Объём за год** (те же ×10 допущения): ~800 тыс. попыток, ~80 млн событий ≈ 30–40 ГБ. Диск 512 ГБ из ТЗ — достаточно; события старше полугода можно чистить дешёвым DELETE по BRIN (см. Р11 — почему они не партиционированы).

## 4. Почему без PgBouncer

PgBouncer решает одну проблему: **много клиентских процессов, каждому нужно соединение** (классика PHP/форк-модели, serverless). У нас её нет:

- Клиент БД ровно один — Go-монолит. `pgxpool` — это уже пул: 20–30 соединений мультиплексируют тысячи горутин. AI-сервис в БД не ходит (общается с ядром по REST).
- Лишний сетевой hop добавляет латентность каждому запросу — при цели «отклик ≤2 с» это чистый минус без выгоды.
- В transaction-pooling режиме ломаются prepared statements (pgx использует их кэш по умолчанию) и session-level фичи — пришлось бы решать проблему, которую сами и создали.
- Это ещё один компонент в изолированном контуре: конфиг, мониторинг, точка отказа.

**Когда понадобится:** go-core масштабирован горизонтально до десятков инстансов и суммарное число желаемых соединений превышает разумный `max_connections` (~100–200). Тогда PgBouncer в transaction mode перед PG — стандартный ход. Заложено: приложение не полагается на session-level состояние БД (нет advisory locks через сессии, временных таблиц между транзакциями), поэтому включение PgBouncer позже — операция конфигурации, не переписывания.

## 5. Ключевые решения

Формат: **Решение → Почему → Отвергнутые альтернативы.**

### Р1. UUID как PK, генерирует приложение (UUIDv7); журналы — bigint identity

**Почему.** UUID нужен API-сущностям: id генерится в Go до INSERT (меньше round-trip'ов, проще батчинг и идемпотентность), не перечислим перебором, безопасен в URL. Классическая беда uuid v4 — случайные вставки размазываются по btree и раздувают индекс — снимается UUIDv7 (время в старших битах → вставки монотонны, как у serial). `DEFAULT gen_random_uuid()` остаётся страховкой для ручных INSERT. Журналы (`attempt_events`, `xp_ledger`, `audit_log`) — `bigint identity`: в 2 раза компактнее uuid, а глобальная уникальность им не нужна, наружу их id не отдаём.
**Альтернативы.** Чистый bigserial везде — перечислимость id наружу, невозможность генерить id на клиенте. Чистый uuid v4 — bloat индексов на самой массовой таблице. ULID/KSUID — то же, что v7, но нестандартный тип (хранили бы text — 36 байт вместо 16).

### Р2. Формы — jsonb; реляционно — только то, по чему ищем и считаем

**Почему.** Карточка происшествия — глубокая изменчивая форма (опросная карта зависит от категории). Реляционная развёртка = EAV или десятки таблиц, которые придётся мигрировать при каждой правке формы фронтендером. jsonb валидируется JSON-схемами (`docs/contracts/`) на границе API — те же схемы использует фронт и ai-service: один источник истины для всей команды из 4 человек. При этом всё, что нужно фильтрам/статистике (статусы, баллы, тайминги, категории), вынесено в колонки — по jsonb мы не ищем, GIN-индексы не нужны.
**Альтернативы.** Полная нормализация — недели работы и хрупкость при живом ТЗ. Всё в jsonb («MongoDB в Postgres») — теряем FK, CHECK и дешёвую аналитику.

### Р3. text + CHECK вместо ENUM

**Почему.** `ALTER TYPE ... ADD VALUE` не работает в транзакции (до PG12 включительно — боль в миграциях), удалить значение из ENUM нельзя вовсе. CHECK меняется одной дешёвой миграцией. Производительность сравнима.
**Альтернативы.** ENUM — экономия байт, не стоящая операционной негибкости. Таблицы-справочники для статусов — оверкилл для значений, зашитых в код.

### Р4. Эталоны — иммутабельные версии

**Почему.** Преподаватель правит эталон *после* того, как по старому уже выставлены оценки. Если эталон мутабелен — оценка необъяснима («почему 62? эталон-то другой»). Версия фиксируется в `attempts.etalon_id` при выдаче; `evaluations.etalon_id` хранится отдельно — переоценка по новой версии возможна и остаётся видимой (какая версия реально использовалась). Частичный уникальный индекс `WHERE is_current` гарантирует ровно одну текущую версию.
**Альтернативы.** Мутабельный эталон + копия в attempt — дублирование килобайтных jsonb в каждой попытке. Полный event sourcing эталонов — незачем.

### Р5. Тайминг — метки событий, не «длительность»; `attempt_events` — источник истины

**Почему.** ТЗ требует сравнение со временем норматива, время реакции, live-мониторинг и отчёт «где ученик тормозит». Одно поле `duration` этого не даёт; набор меток (`issued_at`, `call_accepted_at`, `first_input_at`, `submitted_at`) + поток событий — даёт всё, включая восстановление состояния после обрыва WS: ядро перечитывает события попытки и продолжает. `time_spent_ms` денормализован для отчётов осознанно (правило: вычисляется только из меток).
**Альтернативы.** Хранить только агрегаты — теряем аналитику и восстановление. Полный event sourcing всей системы (состояние = проекция событий) — красиво, но команда из 4 человек на хакатоне утонет; у нас «event sourcing lite»: события дополняют реляционное состояние, не заменяют его.

### Р6. Идемпотентность записи: `client_seq`

**Почему.** ТЗ: восстановление ≤30 с **без потери данных**. Реальный сценарий: клиент отправил батч событий, сеть упала до ACK, после reconnect шлёт повторно. Без дедупликации получим дубли (испорченная статистика «сколько раз менял поле»), с дедупликацией на клиенте — потери. Классическое решение: клиент нумерует события сквозным `client_seq`, сервер пишет `ON CONFLICT DO NOTHING` по частичному уникальному индексу `(attempt_id, client_seq)`. Ретрай безопасен всегда.
**Альтернативы.** Дедуп по хэшу payload — ложные срабатывания (два одинаковых нажатия — легально). Exactly-once на транспорте — не существует.

### Р7. Черновики в отдельной таблице `attempt_drafts`

**Почему.** Автосохранение — самый частый UPDATE в системе (каждые 1–2 с на активного студента). Если черновик — колонка в `attempts`: каждый UPDATE создаёт новую версию строки (MVCC), а при 3 индексах таблицы HOT-оптимизация часто срывается → пухнут и heap, и индексы, autovacuum не успевает, страдают все чтения попыток. Отдельная таблица: PK-only, `fillfactor 50` → место для HOT в каждой странице, обновление не трогает ни одного индекса. Плюс upsert без триггера — минус вызов plpgsql на самой горячей операции.
**Альтернативы.** Черновик только в `attempt_events` — восстановление требует replay всех событий (медленнее и сложнее в Go). Redis — лишний компонент и место, где данные *могут* потеряться (ТЗ прямо запрещает). UNLOGGED таблица — теряется при crash recovery целиком, тот же конфликт с ТЗ.

### Р8. XP — append-only журнал + справочник `levels`

**Почему.** Журнал (`xp_ledger`) вместо счётчика в `users`: начисления объяснимы студенту («+10 за карточку, +5 за норматив»), пересчитываемы при смене правил, не расходятся с фактами при сбоях (сумма = истина). Идемпотентность начислений — уникальный индекс `(attempt_id, reason)`: ретрай обработчика не начислит дважды. `levels` — таблица, а не массив в settings: админ редактирует названия/пороги из UI, фронт получает бейджи, FK-целостности это не требует, но читаемость и UI выигрывают.
**Альтернативы.** Счётчик с инкрементом — быстрее на чтение, но необъясним и расползается; на наших объёмах `sum()` по индексу user_id — микросекунды. Пороги в settings jsonb (как было) — работало, но названия уровней всё равно где-то хранить.

### Р9. Оценка: слои + GENERATED итог + override только с причиной

**Почему.** Три слоя проверки (поля/грамматика/семантика) + тайминг — отдельные колонки: по ним строится аналитика («у группы хромает грамматика»), и они приходят асинхронно (`status='partial'`: поля посчитаны Go мгновенно, AI-слои доедут). `final_score` — `GENERATED ALWAYS AS (COALESCE(override_score, total_score))`: невозможно забыть учесть override ни в одном запросе. CHECK «override требует автора и причины» + запись в audit_log — прямое требование ТЗ («изменение оценок без фиксации в журнале аудита» запрещено). `engine` (модель, версия промпта, версия правил) — воспроизводимость для QA модели.
**Альтернативы.** Пересчитывать итог в Go и хранить одно число — теряем слои для аналитики. Отдельная таблица оценок-версий — оверкилл; переоценка перезаписывает строку, история значимых изменений и так в аудите.

### Р10. Самостоятельная практика = `lessons.kind='practice'`, а не nullable `lesson_id`

**Почему.** Тренажёру нужна работа студента вне занятия (и это дорога к «программе уровней», если решим её делать). Вариант «attempts.lesson_id NULL + practice_id» ломает `UNIQUE (lesson_id, user_id, seq_no)` и плодит CHECK'и на каждую выборку. Вместо этого практика — то же занятие, но `kind='practice'` без преподавателя (CHECK: у class преподаватель обязателен): одна модель попыток, весь пайплайн выдачи/оценки/отчётов работает без единого if. Стандартный приём «унифицируй контекст, а не ссылку».
**Альтернативы.** Отдельная таблица practice_sessions — дублирует lessons на 90%. Не делать практику — режем фичу продукта ради одной колонки; сейчас она стоит два поля и CHECK.

### Р11. `audit_log` партиционирован помесячно; `attempt_events` — нет

**Почему аудит — да.** Хранение ≥6 мес (ТЗ) означает регулярное удаление старого. DELETE миллионов строк = долгий vacuum-долг и bloat; `DROP PARTITION` — мгновенный и бесплатный. Партиции на год создаются в миграции (DO-блок), дальше — ежемесячный job в go-core; DEFAULT-партиция страхует от потери записи, если job не отработал. PK `(at, id)` включает ключ партиционирования (требование PG) и заодно даёт индекс по времени.
**Почему события — нет.** На партиционированной таблице нельзя `UNIQUE (attempt_id, client_seq)` без включения `at` в ключ — а этот индекс держит идемпотентность (Р6), которая важнее: ретеншн событий не регламентирован ТЗ, объём умеренный (~30–40 ГБ/год в пессимистичной оценке), чистка дешёвым batched DELETE по BRIN. Осознанный trade-off.
**Альтернативы.** pg_partman/TimescaleDB — лишние расширения в изолированном контуре. Не партиционировать аудит — можно, но тогда ретеншн = вечный DELETE-долг.

### Р12. Очередь AI-задач — в PostgreSQL (`ai_jobs`, SKIP LOCKED)

**Почему.** Генерация сценариев и AI-слои оценки — минуты (Ollama на CPU/GPU сервера учебного класса). Их нельзя делать в HTTP-запросе; нужна очередь с ретраями, переживающая рестарт. `SELECT ... FOR UPDATE SKIP LOCKED` — стандартный паттерн очереди в PG: транзакционность заданий вместе с данными (оценка и job коммитятся атомарно), ноль новых компонентов в изолированном контуре, ~10 заданий/мин нагрузки. `run_after` — экспоненциальный backoff (не долбим упавший Ollama), `dedup_key` — защита от дублей, `locked_by/locked_at` — requeue зависших.
**Альтернативы.** Redis/RabbitMQ/Kafka — оправданы от тысяч заданий/с и многих потребителей; здесь это компонент ради компонента, плюс двухфазность «данные в PG, задание в брокере» (потерянные/осиротевшие задания). In-memory очередь в Go — не переживает рестарт (ТЗ: автоматическое восстановление сервисов).

### Р13. Кэш TTS — глобальный, по хэшу содержимого

**Почему.** Ключ — `sha256(text|voice|rate)`: одинаковая реплика в разных сценариях («Алло, вы меня слышите?») озвучивается один раз. Привязка кэша к сценарию (как в v1) конфликтовала с этим: UNIQUE по хэшу + scenario_id в одной таблице означали, что вторая вставка либо падает, либо врёт о принадлежности. Content-addressed store — правильная модель: сценарий ссылается на хэш из `call_script`, файл живёт в volume. `last_used_at` (обновляется лениво, батчем) — для LRU-очистки диска.
**Альтернативы.** Кэш per-scenario — дубли файлов и место на диске. Генерировать на лету без кэша — латентность звонка и лишняя нагрузка на GPU в момент занятия.

### Р14. Soft delete + частичные уникальные индексы

**Почему.** ТЗ: результаты обучения сохраняются, ученик не может удалить их; аудит — тем более. Физического DELETE в домене нет: `deleted_at`/`archived_at`. Следствие, которое часто упускают: `UNIQUE(login)` блокировал бы логин навсегда — уникальность объявлена частичным индексом `WHERE deleted_at IS NULL` (удалённый Иванов не мешает новому). FK журналов — без CASCADE: журнал не умирает вслед за чем-либо.
**Альтернативы.** Физическое удаление + архивные таблицы — двойная схема и джойны через UNION.

### Р15. Витрины — VIEW, не materialized и не таблицы-агрегаты

**Почему.** Честный расчёт: 100–200 студентов × тысячи попыток = сотни тысяч строк; агрегаты по индексированным колонкам — единицы миллисекунд. Инкрементальные агрегатные таблицы = код поддержки + баги рассинхронизации, которые нечем окупить. Это осознанное «не-бигтех» решение: настоящий бигтех-подход — считать, а не карго-культить.
**Граница пересмотра:** p95 запроса витрины > 100 мс или миллионы попыток → перевести конкретную витрину на инкрементальный upsert из обработчика оценок (схема этого не запрещает: VIEW заменяется таблицей с тем же контрактом колонок, API не меняется).

## 6. Безопасность и ПДн

- Пароли — только argon2id-хэш; политика первого входа (`must_change_password`), lockout (`failed_login_count`, `locked_until`).
- Сессии отзываемы (`auth_sessions.revoked_at`) — блокировка пользователя убивает вход немедленно.
- **Контракт приложения:** `audit_log.before/after` редактируются до записи — `password_hash`, токены и т.п. в журнал не попадают. (В БД это не выразить — закреплено комментарием в схеме и здесь.)
- ПДн: `consent_given_at`; ФИО студентов не попадают в `scenarios`/`etalons` (там вымышленные заявители); доступ к чужим результатам режется RBAC на уровне API.
- TLS внутри контура — конфигурация PG (`ssl=on`) и reverse-proxy, не схема.

## 7. Эксплуатация (сервер из ТЗ: 6+ ядер, 32 ГБ, NVMe)

Конфиг PG (стартовые значения):

```
shared_buffers = 8GB              # 25% RAM
effective_cache_size = 24GB
random_page_cost = 1.1            # NVMe
max_connections = 100             # реальный пул pgxpool ~25
max_wal_size = 4GB
checkpoint_completion_target = 0.9
wal_compression = on
synchronous_commit = on           # off — per-transaction для событий (SET LOCAL)
shared_preload_libraries = 'pg_stat_statements'
autovacuum_vacuum_scale_factor = 0.05   # per-table для attempts, attempt_drafts
```

- **Бэкапы** (ТЗ: ≥1 раз в сутки): `pg_dump` по расписанию из go-core, журнал в `backups` (путь, размер, sha256 — админ видит в UI, ТЗ это требует).
- **Партиции аудита**: ежемесячный job — создать партицию M+1, дропнуть старше `audit_retention_days`; алерт админу, если в DEFAULT-партиции появились строки.
- **Ретеншн событий**: batched DELETE `attempt_events` старше N мес (по BRIN — дёшево), с паузами.
- **Мониторинг** (ТЗ: «интеграция с локальными средствами мониторинга»): go-core экспортирует `/metrics` (Prometheus-формат), включая длину очереди `ai_jobs`, лаг оценок, размер партиций.

## 8. Чего сознательно нет (и когда пересмотреть)

| Не сделано | Почему | Триггер пересмотра |
|---|---|---|
| PgBouncer | §4: один клиент-монолит с pgxpool | Десятки инстансов go-core |
| Шардинг / реплики чтения | 1 узел держит нагрузку ×10 от ТЗ | Не в рамках учебного контура |
| Брокер сообщений (Kafka/Rabbit) | Р12 | Тысячи AI-задач/с, внешние потребители |
| Redis-кэш | Нечего кэшировать: горячие данные и так в shared_buffers | p95 чтений > целевых при профилировании |
| CQRS / отдельная read-БД | Витрины-VIEW достаточны (Р15) | Миллионы попыток, тяжёлая аналитика |
| Программа уровней-заданий (level_tasks, unlock-правила) | Продуктовая фича вне ТЗ; XP-уровни есть, практика есть (Р10) — фундамент готов | Решение команды делать «кампанию»; добавляется таблицами `level_tasks` + `student_level_progress` без миграции существующих |
| История паролей | ТЗ не требует; в изолированном контуре ценность мала | Требование ИБ заказчика |
| Микросервисные БД (per-service) | Монолит + один PG — осознанная архитектура проекта | — |

## 10. Миграция 00002 — голосовой режим и ядро go-core

Файл: [`db/migrations/00002_go_core_voice.sql`](../db/migrations/00002_go_core_voice.sql). Всё аддитивно,
Down-миграция полная. Решения:

- **Р16. Транскрипт — `attempt_dialogue_turns`, PK `(attempt_id, turn_no, speaker)`.** `turn_no` — номер
  *обмена*, как его видит фронт (`DialogueTurnView.turnNo`): 0 — вступление заявителя, k — k-я реплика
  оператора и ответ на неё. Повтор хода после обрыва упирается в PK — идемпотентность без отдельного
  ключа. Реплики «нет речи» не сохраняются вовсе (номер не расходуется). Для ai-service транскрипт
  перенумеровывается сквозным `turn_no` 1..n на лету (`convert.ExchangeToSeq`). Аудио оператора не
  хранится нигде (ПДн, диск) — только текст и уверенность STT. *Альтернатива:* реплики в `attempt_events` —
  отвергнута: транскрипт читается целиком на каждый ход диалога и в отчёте, а события — телеметрия
  с другим профилем записи и ретеншном.
- **Р17. Состояние разговора — колонки `attempts.call_ended_at / call_end_reason / dialogue_turns`.**
  Читаются в каждом `Attempt`; отдельная таблица «разговоров» 1:1 к попытке не нужна.
- **Р18. `attempts.incident_no` из sequence** — номер происшествия в шапке карточки АРМ, монотонный,
  человекочитаемый, не зависит от UUID.
- **Р19. Оценка: `dialogue_score` + `dialogue`, `layers`, `weights`, `needs_review`, `ai_unavailable`,
  `grammar_stats`.** Слои приходят асинхронно — `layers` хранит их терминальные состояния
  (`running` накладывается при чтении из `ai_jobs`, чтобы не писать в `evaluations` на каждом
  переходе задачи). `weights` — фактические веса итога после перенормировки: UI показывает их,
  а не хардкодит, и итог объясним задним числом. Флаги ревью — колонки, по ним идёт выборка
  «что проверить преподавателю» (частичный индекс `evaluations_review_idx`).
- **Р20. `etalons.card_draft` рядом с `card`.** `card` — контрактный `IncidentCard` (snake_case) уходит
  в ai-service; `card_draft` — та же эталонная карточка в форме АРМ (`IncidentCardDraft`), с ней
  go-core сверяет карточку студента (слой 1). Проекции взаимно однозначны там, где это важно,
  и живут в `internal/convert`. `expected_dialogue` — чек-лист разговора (контракт v1.1).
- **Р21. Версии сценария — `scenarios.parent_id / version`.** Сценарий, стоящий в занятии, не правится
  (результаты должны быть объяснимы) — создаётся новая версия-копия; эталоны внутри сценария
  по-прежнему версионируются иммутабельно (Р4).
- **Р22. Классификатор: `synonyms`, `reference`, `featured`, `sort_order`, `service_rules`.** Поиск по
  Инструкции п.4.2, справка по типу, плашки «частые/значимые», правила определения служб — данные,
  а не код: правятся импортом, не релизом.
- **Р23. Коды служб 101..104 (GAP-08)** — как в реальном АРМ-112; `short_name` — подпись на плашке.
- **Р24. XP: `pass_bonus`, частичный уникальный индекс на `lesson_completed`** — идемпотентность
  начислений за занятие (у них нет `attempt_id`).
- **Р25. Настройки голоса и эксплуатации в `settings`** (`voice`, `stt`, `confidence_threshold`, `ai`,
  `login`, `backup`, `events_retention_days`, `dialogue_weight_default`). Веса по умолчанию получили
  `dialogue: 0` — при включении голоса вес разговора берётся из `dialogue_weight_default`, остальные
  слои ужимаются пропорционально (та же логика, что во фронте).

## 11. Миграция 00003 — постраничные списки

- **Р26. Keyset-пагинация + индексы в порядке сортировки.** `GET /lessons`, `/scenarios`, `/users`,
  `/lessons/assigned` отдают страницу (`?limit`, курсор в `X-Next-Cursor`). Курсор — значения полей
  сортировки последней строки: `(created_at, id)` у занятий и сценариев, `(last_name, first_name, id)`
  у пользователей, `(ранг статуса, created_at, id)` у занятий обучающегося. Следующая страница —
  индексный диапазон «после курсора» + `LIMIT`: читается ровно страница, сколько бы строк ни
  накопилось. Индексы `lessons_created_idx`, `lessons_teacher_created_idx`, `scenarios_created_idx`,
  `users_name_idx` — ровно в порядке сортировки списков (проверено тестом плана на 5000 строк: над
  сканом нет `Sort`). Первая страница — тот же SQL с граничным курсором: один текст запроса,
  план всегда индексный. `count(*)` не считаем — «есть ли дальше» узнаём по `LIMIT n+1`.
  *Альтернатива:* `OFFSET` — отвергнута: страница 200 заставляет PostgreSQL прочитать и
  выбросить 20 000 строк, и тяжёлые строки списка (участники занятия, легенда и эталон
  сценария) превращают это в нагрузку, которая растёт с глубиной листания.

## 12. Миграция 00004 — ракурс «Диспетчер ДДС»

- **Р27. Служба обучающегося — колонка `attempts.service_id`, а не вывод из профиля.** В ракурсе
  dds (контракт v1.3) обучающийся работает за диспетчера конкретной службы: статусы реагирования
  он проставляет только ей, оценка сверяет протокол этой службы. Служба выбирается при выдаче
  карточки (профиль ДДС `users.service_id`, если его служба в списке оповещения сценария; без
  профиля — основная служба карточки) и фиксируется в попытке, как `etalon_id`: профиль могут
  поменять посреди занятия, а права на статусы и оценка должны остаться объяснимыми задним
  числом. Колонка же — признак ракурса у попытки: горячий путь автосохранения решает «dds или нет»
  по строке попытки без JOIN занятия, а попытки, выданные до миграции (NULL), работают по-старому.
  Эталон работы диспетчера (`decision`, `decision_within_sec`, `required_statuses`) — ключ
  `reaction` в `etalons.scoring` (jsonb): версионируется вместе с эталоном, миграции не требует.
  *Альтернатива:* `lessons.settings.perspective` + `users.service_id` на лету — отвергнута:
  смена профиля меняла бы права и оценку уже выданных карточек.
