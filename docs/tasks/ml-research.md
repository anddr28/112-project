# Задачи: выбор и проверка моделей (bench)

Владельцы: питонист (скрипты, запуск) + QA (датасеты, разметка, слепые оценки).
Результат: `docs/model-selection.md` (model card проекта — ТЗ требует «описание методов
и ограничений») и заполненный `ai-service/config/models.yaml`. Код и данные —
`ai-service/bench/`.

Зачем это отдельная работа: жюри и техэкспертиза спросят «почему эта модель и
насколько ей можно верить». Ответ должен быть таблицей с цифрами на наших данных,
а не «Qwen хорош в русском».

## 0. Стенд и правила

- **Стенд** — x86-ноутбук 8 ядер / 16 ГБ (целевой профиль заказчика). Замеры на
  Apple Silicon **не считаются** (в 3–5 раз быстрее на CPU) — можно только для отладки
  скриптов; в отчёте колонка «стенд» обязательна.
- Всё, что скачивается, — заранее списком (QA-01): Ollama-модели, whisper, silero.
- Один и тот же `seed`, `temperature` и версии промптов во всех прогонах; отчёт
  пишется скриптом в `bench/reports/<date>-<component>.md`, руками — только выводы.
- Слепые человеческие оценки: рейтер не знает, какая модель; порядок перемешан;
  ≥ 2 рейтера; фиксируем согласие (простой процент совпадений или каппа).

Структура:
```
ai-service/bench/
  README.md                 # как повторить каждый bench одной командой
  data/
    stt/{audio/*.webm|wav, manifest.csv}                 # QA-04
    dialog/scenarios.json, operator_scripts.json         # ML-02
    golden/attempts.jsonl, transcripts.jsonl, labels.csv # QA-06
    tts/phrases.txt
    grammar/{clean.txt, seeded_errors.csv}
    gen/specs.json
  scripts/
    stt_eval.py  caller_eval.py  judge_eval.py  tts_eval.py  lt_eval.py  gen_eval.py  load_dialog.py
  reports/
```

## ML-01 — STT: движок для речи оператора *(первым; нужен датасет QA-04)*

**Кандидаты** (все CPU, офлайн):

| Движок | Почему смотрим | Ожидания |
|---|---|---|
| faster-whisper `small` int8 (baseline) | быстро, есть `initial_prompt` под hints | WER ~15–20 % на бытовой речи, RTF ~0.3 |
| faster-whisper `medium` int8 | точнее | RTF ~0.8 — вероятно медленно |
| faster-whisper `large-v3-turbo` int8 | лучший whisper по качеству | на CPU может не уложиться — проверить |
| GigaAM-v2 CTC / RNNT (Sber, ONNX) | лучший WER на русском среди открытых (≈ 2–3× ниже whisper-small) | быстрый; нет `initial_prompt`, нужен ITN; проверить офлайн-загрузку и лицензию |
| Vosk `vosk-model-ru-0.42` / `small-ru-0.22` | стриминг «из коробки», крошечный | хуже качество на числах/адресах |

**Датасет** (QA-04, `manifest.csv`: `file, speaker, text_ref, category, noise, duration_ms`):
- 4 диктора × 25 фраз = 100 реплик, по 5 категорий: адреса с числами («Ленина дом
  четырнадцать корпус два подъезд три этаж пять»), телефоны, ФИО, протокольные
  фразы («Служба сто двенадцать, слушаю», «помощь направлена, оставайтесь на связи»),
  описания происшествия; + короткие «да», «понял», «повторите».
- +20 реплик с шумом (наложить `bench/data/noise/office.wav` при SNR 10 дБ скриптом)
  и 10 файлов «тишина/шум без речи» для `no_speech`.
- Запись **через наш же фронтовый рекордер** (webm/opus, как в проде) — плюс wav 16 кГц
  из Audacity для 20 фраз (проверить, что декод не портит).

**Метрики** (`stt_eval.py`, `jiwer`): WER и CER после единой нормализации (нижний
регистр, без пунктуации, `itn_ru` с обеих сторон); **точность адресных сущностей**
(все числа дом/корпус/подъезд/этаж/квартира совпали — да/нет; это важнее WER);
точность телефонов (11 цифр подряд); `no_speech` precision/recall; галлюцинации на
шуме (вывод непустого текста на файле без речи); RTF, p50/p95 задержки на 5-секундной
реплике, RAM; эффект `initial_prompt` с hints (whisper: с/без).

**Правило выбора**: (1) адресная точность ≥ 85 % и `never`-галлюцинаций на тишине
≤ 5 %; (2) RTF ≤ 0.5; среди прошедших — минимальный WER; при разнице WER < 2 п.п. —
более быстрый. Итог — `STT_ENGINE` + профиль `stt_default` + список правил ITN,
которые пришлось добавить.

## ML-02 — LLM-заявитель (dialog_fast) *(после PY-07 и сценариев QA-05)*

**Кандидаты** (Ollama library или GGUF с HF, q4_K_M):

| Модель | Размер | Комментарий |
|---|---|---|
| `qwen2.5:3b-instruct` (baseline) | ~2 ГБ | уже выбран для оценки; быстрый |
| `qwen2.5:7b-instruct` | ~4.7 ГБ | лучше держит роль; медленнее ×2 |
| `qwen3:4b`, `qwen3:8b` | ~2.6 / ~5 ГБ | **выключить thinking** (`/no_think`), иначе задержка ×5 |
| `gemma3:4b` | ~3.3 ГБ | хороший русский, слабее в JSON |
| YandexGPT-5-Lite-8B-instruct (GGUF) | ~5 ГБ | русскоязычная нативно; проверить лицензию для конкурса |
| T-lite-it-1.0 (8B, GGUF) | ~5 ГБ | русский fine-tune Qwen2.5 |
| Vikhr-Gemma-2B / Vikhr-Qwen-2.5-7B | ~1.6 / ~4.7 ГБ | русские fine-tune'ы |
| `qwen2.5:1.5b-instruct` | ~1 ГБ | аварийный профиль, если всё медленно |

**Протокол** (`caller_eval.py`): 8 сценариев (`data/dialog/scenarios.json` — по одному
на категорию, с брифом: 2 `volunteer`, 3 `on_request`, 1 `never`, 2 `unknowns`) ×
3 сценария поведения оператора (`operator_scripts.json`: «хороший» — спрашивает
всё по протоколу; «плохой» — не спрашивает адрес, грубит; «хаотичный» — переспрашивает,
перебивает вопросами не по делу) × 6 ходов = 144 хода на модель. `temperature 0.4`,
`seed 42`. Прогон через реальный `POST /v1/dialog/turn` текстом (тот же промпт, что в проде).

**Автоматические метрики**:
- `never`-утечка: текст `never`-факта (ключевые слова) в реплике — **должно быть 0**;
- ранняя утечка `on_request`: факт прозвучал до того, как в реплике оператора
  встретились его `hints` — доля от всех `on_request`;
- выдуманные факты: новые адреса/числа/имена, которых нет в брифе (регулярки на числа
  и заглавные слова + судья-LLM 7b «есть ли в реплике факт, отсутствующий в брифе»);
- ответ на `unknowns` содержит «не знаю/не вижу/не могу сказать» — доля;
- валидный JSON с первого раза — доля; длина ≤ 40 слов — доля; `should_end` не раньше
  3-го хода — доля;
- задержка: `prompt_eval` мс, генерация ток/с, полный ход p50/p95 при промпте ~700 ток.;
- **пропускная способность**: `load_dialog.py` — 1 / 2 / 4 / 8 одновременных диалогов
  при `OLLAMA_NUM_PARALLEL` = 1 / 2 / 4: p50/p95 хода, RAM. Это число идёт в
  документацию как «сколько студентов одновременно говорят на CPU-стенде».

**Человеческая оценка** (QA + один из команды, слепая): 30 случайных реплик на модель,
1–5 по «звучит как живой заявитель в этой ситуации» и «соответствует персоне/эмоции».

**Правило выбора**: `never` = 0, ранняя утечка ≤ 10 %, выдумки ≤ 5 %, JSON ≥ 98 %,
p50 хода ≤ 4 с на стенде → среди прошедших лучшая человеческая оценка.
Если 7b проходит по качеству, но не по времени — остаётся 3b, а 7b — только для
`eval_thorough` ночью.

## ML-03 — LLM-судья: семантика и оценка разговора *(последним из bench; нужен golden set QA-06)*

**Golden set** (QA-06: сначала ≥ 40 попыток, к финалу — 60): смесь реальных прогонов
команды (мы сами «студенты»: хороший / средний / плохой оператор) и синтетических
вариаций (в хороший ответ вносим потерю факта, домысел, грубость). Для каждой:
`card.description` + транскрипт разговора + эталон с `required_facts` и чек-листом.

**Разметка** (`labels.csv`, делает QA; 15 попыток размечают двое — считаем согласие):
- по каждому `required_fact`: `present | partial | missing`; список домыслов;
- по каждому пункту чек-листа: `done | partial | missed` + номер реплики-доказательства;
- общий балл 0–100 за текст и за разговор по рубрике (в `bench/data/golden/RUBRIC.md`);
- «нужен ли ревью преподавателя» (да/нет) — для калибровки `confidence`.

**Метрики** (`judge_eval.py`): точность статусов фактов и пунктов (accuracy, macro-F1
по `missing`); Spearman и MAE между `score` из `scoring.py` и человеческим баллом;
калибровка `confidence`: доля ошибочных оценок в корзинах `<0.5 / 0.5–0.7 / 0.7–0.9 / >0.9`
(должна падать); детерминизм: 5 прогонов одного входа при `temperature 0` → одинаковый
результат; A/B версий промптов (`semantic/v1` vs `v2`, `dialogue_eval/v1` vs `v2`).

**Модели**: `qwen2.5:3b` vs `qwen2.5:7b` (и победитель ML-02, если другой).
Решение о памяти: если 3b отстаёт от 7b по Spearman < 0.05 — **всё на 3b** (одна модель
в RAM, нет свапа). Иначе 7b для `eval_dialogue`/`eval_thorough` строго после занятия.

**Цели**: статусы фактов ≥ 85 %, пункты чек-листа ≥ 80 %, Spearman ≥ 0.7,
`confidence < 0.7` ловит ≥ 70 % случаев «нужен ревью».

## ML-04 — TTS: голоса и произношение *(после PY-08, параллельно ML-01)*

- Silero v4 ru: `aidar, baya, kseniya, xenia, eugene` — 15 фраз (`data/tts/phrases.txt`:
  адреса с числами, телефон, сокращения, паническая реплика, спокойная) после `textnorm`.
- **Тест разборчивости** (важнее MOS): 3 слушателя записывают услышанный адрес/телефон
  → доля точных совпадений; цель ≥ 95 % после нормализации текста.
- MOS-lite 1–5 (естественность) — 3 рейтера, слепо по голосам; выбрать 2 голоса
  (женский/мужской) + маппинг `caller.role/age` → голос.
- Эмоция: SSML `<prosody rate="1.15" pitch="+10%">` для «паника» — субъективно лучше/хуже.
- RTF на стенде; альтернативы только если Silero провалит разборчивость: Piper
  (`ru_RU-irina-medium`, `ru_RU-denis-medium`), vosk-tts (ru, multi-speaker).

## ML-05 — LanguageTool: шум и формула *(после PY-03, параллельно ML-01)*

- `data/grammar/clean.txt` — 50 корректных текстов оператора с адресами, сокращениями,
  фамилиями → ложные срабатывания на 100 слов **до** и **после** списка исключений
  и словаря домена (цель ≤ 1 на 100 слов).
- `seeded_errors.csv` — 30 текстов с внесёнными ошибками (опечатки, пропущенные запятые,
  падежи) → recall по типам.
- Калибровка `gr-v1`: чистый текст = 100; 1 опечатка на 30 слов ≈ 85–90; «поток без
  знаков и с 5 ошибками» ≈ 40–50. Подобрать коэффициенты, зафиксировать как `gr-v1`
  (или `v2`, если меняли после первого релиза).

## ML-06 — качество генерации сценариев *(после PY-10)*

- 4 категории × 5 генераций × 2 модели (3b, 7b) через реальный `/v1/jobs/generate`.
- Автоматически: доля прошедших валидацию с первого раза, время, дубли заголовков.
- Рубрика 1–5 (QA + лид): реализм легенды; согласованность карточки, легенды и фактов;
  использование признаков опросной карты категории; полезность чек-листа (пункты
  специфичны для категории, а не только базовые); соответствие сложности.
- Итог: модель для `generate`, few-shot по категориям дополнены лучшими образцами.

## ML-07 — `docs/model-selection.md` *(в самом конце)*

Шаблон разделов: «Стенд» → по компоненту (STT / LLM-заявитель / LLM-судья / TTS / LT /
генерация): кандидаты, датасет (размер, кто записал), метрики таблицей, решение,
конфиг (`models.yaml` фрагмент), известные ограничения, как повторить (`make bench-*`).
Плюс раздел «Ограничения на CPU-стенде»: одновременных диалогов N при p95 ≤ M с;
что даёт GPU (оценочно). Это идёт в презентацию и в документацию ТЗ.
